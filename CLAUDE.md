# TNT Run — s&box

Multiplayer arena game. Players run across a tiled floor; every tile they step on
collapses after a fraction of a second. Fall through and you land on the floor below.
Fall past the last floor into lava and you're out. Last player alive wins the round.

Target: 24 players, auto-matchmaking, ranks. **None of that is in scope yet** — see Scope below.

## Constants (single source of truth)

Put these in one static class. Do not scatter magic numbers.

```csharp
public static class Arena
{
    public const int   GridSize      = 30;    // tiles per side, per floor
    public const float TileSize      = 56f;   // world units (s&box unit ≈ 1 inch)
    public const float TileThickness = 12f;
    public const int   FloorCount    = 5;
    public const float FloorGap      = 220f;  // vertical spacing between floors
    public const float DecayDelay    = 0.6f;  // seconds from step-on to disappear
    public const float LavaOffset    = 250f;  // below the lowest floor
}
```

Scale: Citizen is ~72 units tall, so a 56-unit tile is roughly a Minecraft block relative
to the player. 30×30×5 = 4500 tiles.

## Architecture — three decisions that are not negotiable

These exist because the naive version does not survive 4500 tiles × 24 players.

**1. Tiles are disabled, never destroyed.**
`GameObject.Enabled = false` on collapse. Round restart is one loop re-enabling everything.
Destroying and respawning 4500 GameObjects per round will stall the game.

**2. Tile lookup is arithmetic, not a trace.**
Never raycast down every frame to find the tile under a player. Compute it:
`tileX = (int)((pos.x - originX) / TileSize)`, same for Y, and derive the floor index from Z.
O(1), zero physics cost. Store tiles in `GameObject[,,]` indexed `[floor, x, y]`.

**3. Tile collapses are batched into one RPC.**
Do **not** put `[Sync]` on tiles. The host is authoritative: it accumulates collapsed tile
indices in a buffer and flushes them via a single `[Rpc.Broadcast]` every ~100 ms as a
packed array. Per-tile RPCs at 24 players is hundreds of messages per second.

## Components (build in this order)

| # | Component | Responsibility | Done when |
|---|---|---|---|
| 1 | `ArenaGenerator` | Builds `FloorCount` grids of tiles + lava plane at runtime. Holds `GameObject[,,]`. Exposes `GetTile(floor,x,y)` and `ResetAll()`. | Play mode shows 5 stacked floors of boxes |
| 2 | `TileDecay` | Tracks pending collapses, disables tiles after `DecayDelay`, feeds the RPC buffer. | Walking leaves a trail of holes |
| 3 | `TntPlayer` | Movement (`CharacterController`), maps world position → tile index, marks tiles as stepped-on. | Player falls to the floor below |
| 4 | `LavaZone` | Trigger below the last floor; marks player eliminated. | Falling all the way out eliminates you |
| 5 | `RoundManager` | Round state machine (Waiting → Playing → Ended), spawns players, detects last-alive, resets arena. | Rounds start and restart cleanly |
| 6 | Networking pass | Host authority, player spawn/ownership, batched collapse RPC. | Two clients see the same holes |
| 7 | `Hud.razor` | Alive count, round timer, your floor number. | — |

Stop after each numbered item and let me test it. Do not build ahead.

## Scope

**In scope now:** the seven components above, 2–4 players, one lobby, one hardcoded arena.

**Lobby browser** — promoted from out-of-scope on 2026-08-19. Turn 1 was a console dump of what
`Networking.QueryLobbies()` really returns; turn 2 is the panel (`code/LobbyBrowser.cs` +
`code/ui/LobbyBrowserPanel.razor`). Both closed. Matchmaking proper stays out — this discovers
lobbies, it does not pick one for you. Open caveat: the platform filters your own lobby out of
the results, so discovery by a genuinely separate Steam account is still unverified, and
`"Org": "local"` blocks distribution regardless.

**Three additions opened 2026-08-19**, each with its own limits:

- **Ragdoll on player-player collision.** The host decides when a ragdoll starts. A ragdolled
  body does **not** collapse tiles — only an actively controlled player does. Recovery is a
  straight snap back to controlled movement; no stand-up animation.
- **Asset/visual pass.** See the widened built-in-assets rule above for exactly what this opens.
- **HUD polish.** Presentation work on the existing `Hud.razor` and its stylesheet. Done.

**Two further additions opened 2026-08-19**, after the HUD pass:

- **Full UX flow: menu → lobby → game → result.** One coherent path with a shared shell, rather
  than a browser overlay and a HUD that don't know about each other. Includes a starting screen
  with an explicit host-or-browse choice, which moves lobby creation out of the
  `RoundManager.AutoHost` editor toggle and into a button. Matchmaking still stays out — a menu
  that lets you pick a lobby is not a system that picks one for you.
- **Arena visual/map pass.** Making the arena read as a designed space instead of a test grid:
  tint patterns beyond the pure checker, the per-floor darkening, and a boundary treatment so
  the edge does not trail into void. Built-in assets only, per the widened rule above.
  - This does **not** open "multiple arena layouts", which stays out. One arena, dressed better.
  - Anything that changes the play grid's dimensions, tile count or collision is out. A visual
    rim outside the grid is fine; a rim you can stand on is a layout change.

**Explicitly out of scope:** ranks, persistence, `Sandbox.Services` leaderboards, matchmaking,
player-selectable cosmetics, multiple arena layouts, particle effects, custom models,
custom sounds, fall damage, powerups. Do not add these. Do not write "hooks for later."
If you think one is needed, say so and wait.

("Player-selectable cosmetics" is the thing that stays out — a customisation feature. Dressing
the Citizen from `ClothingContainer` during the asset pass is allowed, per the rule above.)
